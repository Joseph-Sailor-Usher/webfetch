# src: implementation

## The address guard (card-1, 2026-11-27)

- `Guard` (src/lib.rs) is what the guard refuses: `is_private(ip)` or `is_local(ip)`. `is_local` asks the set of this machine's interface addresses read when the guard was built (`local_addrs()`: Linux /proc/net/if_inet6 and the `/32 host LOCAL` entries of /proc/net/fib_trie). For an address added since, or on a system where those can't be read, it also tries to bind a UDP socket to the address. IPv4-mapped IPv6 addresses match their IPv4 form.
- `Guard::check_url` checks the scheme and any literal IP. `Guard::lookup` is the resolver step: it refuses a name if any address it resolves to is refused. `Guard::with_local` and `Guard::with_host` let tests inject the local addresses and the DNS answers.
- `client(guard, ua)` is `client_with(Some(Arc<Guard::from_interfaces()>), ua)`, and its redirect policy and `GuardedResolver` both use that guard. `fetch(client, url, guard)` keeps its signature (mcp.rs and main.rs call it) and delegates to `fetch_with(client, url, Option<&Guard>)`. The free function `check_url(url)` stays public, using a fresh `Guard::from_interfaces()`.
- `--allow-private` (guard false) builds no Guard, so nothing is refused.
- Test: `refuses_this_machines_own_address` in src/lib_test.rs. It covers a literal IP, a resolved name and redirects (by IP and by name) to an injected local address, and checks that a non-local public address passes.

## The URL-provenance gate (card-2, 2026-11-27)

Built to the rule in the src planning note.

- `mcp::Settings` gains `allow_urls`, `allow_domains`, `max_fetches` and `session: Arc<Session>`. `serve` clones Settings into each tools/call thread, so the session state sits behind the Arc. `Session { seen: Mutex<HashSet<String>>, fetches: AtomicU32 }` is `Default`, and main.rs builds it with `session: Default::default()`.
- `normalize_url(url)` (pub) parses with `reqwest::Url` and drops the fragment. Scheme and host are lowercased and the default port is dropped; path and query stay byte for byte. Seen URLs and `--allow-url` values are compared in this form.
- `Settings::may_fetch(url)` is the gate. It passes a URL that is in the seen set or that matches an allow-url, and a URL whose host is an allow-domain or a subdomain of one, at a dot boundary (`host_in`; IPv6 brackets trimmed). Anything else gets `refused: <url> was not returned by this session's search and is not allowed by the operator (--allow-url/--allow-domain); ...`.
- `take_fetch()` counts against `max_fetches` with an atomic `try_update`. Once the cap is spent it returns `fetch limit reached (N per session; --max-fetches)`.
- The order in `fetch_page` is: validate the arguments, then the gate, then the cap, then fetch. A refused URL never counts toward the cap. Every paged call is one fetch.
- `search_tool` adds the normalized URLs of the hits it returns (after `max_results`) to the seen set. Nothing reads links from fetched pages into the seen set.
- The tool description of fetch_page and INSTRUCTIONS tell the agent about the gate.
- main.rs adds `--allow-url`, `--allow-domain` (repeatable) and `--max-fetches` (Option, default 50). They are valid only with `--mcp`: main checks this by hand and exits with code 2, because clap's `requires = "mcp"` did not fire with the required `target` ArgGroup. A bad `--allow-url` also exits with code 2.
- Tests (tests/mcp_test.rs): `fetch_page_refuses_an_unseen_url` covers an unseen URL, a search-returned URL (and the same URL with a fragment), a seen URL with an added query, a link found only inside the page, an `--allow-domain localhost` host and the `evillocalhost` boundary, an exact `--allow-url`, and the cap with `--max-fetches 2`. `the_gate_flags_need_mcp` checks that the CLI refuses the flags without `--mcp`. The existing MCP tests that fetch local pages directly now pass `--allow-domain 127.0.0.1`.
- README: a section "Which URLs fetch_page fetches".

## The body cap (card-3, 2026-11-27)

- `MAX_BYTES` (10,000,000) in src/lib.rs. `fetch` and `fetch_with` keep their signatures and read under it. `fetch_capped(client, url, Option<&Guard>, max_bytes)` is the new entry point.
- After the status check, a `content_length()` over the cap is refused with `refusing <url>: its body is N bytes, over the M-byte cap (--max-bytes)`, before any body is read. Otherwise the body is read through `resp.take(max_bytes + 1).read_to_end`. If more than the cap arrived, the page is marked truncated and cut at `utf8_cut(buf, max_bytes)`, which backs off to the start of any character the cut would split. The body is then decoded with `String::from_utf8_lossy` (no charset sniffing, the same as before for UTF-8 pages).
- `Page` gains `truncated: bool` and `max_bytes: usize`, plus `truncation_notice()` (Option). Page is built only in lib.rs, so mcp.rs still compiles unchanged.
- main.rs: `--max-bytes` (default `MAX_BYTES`; conflicts with `--mcp`). The CLI calls `fetch_capped`. A cut body prints `webfetch: truncated: ...` on stderr and a `[truncated: ...]` line under the label: in the header for Markdown/text output, after the label for `--raw`.
- Not done (outside the card's paths): the MCP fetch_page result still carries the constant NOTICE and no truncation flag. It reads under the default 10 MB cap, but an agent is not told when a page was cut. That needs a change in mcp.rs (for example a `truncated` field and the page's `truncation_notice()`).
- Test: `caps_the_body_it_reads` (src/lib_test.rs). Against an endless stream of `é` with a 100,001-byte cap, the fetch returns (well under the 15 s timeout) with 100,000 bytes of whole characters, marked truncated, and the server stops writing once the reader hangs up. A `Content-Length: 1000000000` reply with no body is refused at once. `http_errors_are_errors` checks that a small body is not marked.
- README: a bullet under Limits, and the exit-status line.

## Redirects to another host (card-4, 2026-11-27)

Built on main at 651420d (card-1 only), so it does not have the card-2 or card-3 code. Merging needs care in `fetch_with`/`fetch_capped` and in `fetch_page`'s order.

- `same_host(from, to)` (pub, src/lib.rs): the hosts match, ignoring case. The ports must match too, unless both URLs are on their own scheme's default port, so `http://a/` to `https://a/` counts as the same host. `www.a` and `a` are different hosts, and so are two different ports.
- `client_opts(guard, ua, follow_any_host)` is the one builder. `client_with(guard, ua)` is `client_opts(.., false)`. `client_following(guard: bool, ua)` is `client_opts(.., true)`, the old behaviour. The redirect policy keeps the 5-hop limit and checks the guard first, so a refused literal IP is refused even on a cross-host hop. Then, unless follow_any_host is set, a hop whose host differs from the first URL's host gets `attempt.stop()`: reqwest returns the 3xx response and makes no request to the target.
- `fetch_or_redirect(client, url, Option<&Guard>) -> Result<Fetched>`, where `Fetched` is `Page(Page)` or `Redirect(Redirect { from, to, status })`. `to` is the Location header resolved against the response URL. `fetch_with` (and so `fetch`) turns a Redirect into `Error(r.message())`: `<from> redirects (302) to another host: <to> - not followed; fetch that URL yourself if you mean to`. The CLI prints it on stderr and exits 1, with no change to main.rs.
- mcp.rs: `ToolOutcome = Result<Value, Failure>`. `Failure` is `Message(String)` or `Redirect(Redirect)`, with `From<String>`/`From<&str>`. `fetch_page` calls `fetch_or_redirect`. A redirect becomes an `isError: true` result. Its `structuredContent` is `{error, url, redirect_url, status}`, and its text names the URL too, for a client that drops structuredContent on an error. That object does not follow fetch_page's outputSchema, which a client may check on a successful result but has no reason to check on an error. The tool description and INSTRUCTIONS tell the agent about it.
- Test: `does_not_follow_a_redirect_to_another_host` (src/lib_test.rs). It covers the `same_host` cases. A same-host 301 is followed. A same-host hop, then a 302 to `localhost:<other>`, comes back as a Redirect. `fetch` returns an error that names the target. `mcp::handle` tools/call returns isError with `redirect_url`. The other server's request counter stays 0 through all of that. `client_following` then reaches the other server (counter 1).
- `refuses_this_machines_own_address` now builds its redirect client with `client_opts(.., true)`. The guard on redirects matters when redirects are followed. The default client gives a cross-host redirect to a name back without resolving it, and the next fetch resolves the name through the guard.
- Not done (outside the card's paths): the CLI's `--follow-redirects` flag. main.rs needs `#[arg(long)] follow_redirects: bool` and a call to `client_following(guard, ua)` instead of `client(guard, ua)` when it is set. README says the flag is still to be wired.
- When merged with card-2: a `redirect_url` handed back is not in the session's seen set, so the provenance gate refuses the agent's follow-up fetch unless the operator allows the target. Decide whether a returned redirect_url should be added to the seen set.

## Proxies and the guard (card-5, 2026-11-27)

Built on main at 082a47c (cards 1 and 2), so it does not have the card-3 or card-4 code. Merging with card-4 means folding `client_opts`' `follow_any_host` and this card's `proxy` into one builder.

- Before this card, `client_with` did not call `.no_proxy()`. reqwest 0.12 reads HTTP_PROXY/HTTPS_PROXY/ALL_PROXY by default, so a guarded client in an environment with a proxy set sent every request to the proxy. The `GuardedResolver` then resolved only the proxy's name, never the target's.
- `client_proxied(guard: Option<Arc<Guard>>, ua, proxy: Option<reqwest::Proxy>)` is now the one builder. With a guard it calls `.no_proxy()` (which turns off the environment's proxies and clears any proxy added before it) before the resolver. Then, if the caller passed a proxy, it calls `.proxy(p)`. An unguarded client given no proxy keeps reqwest's default and uses the environment's proxy (`--allow-private`, SearXNG).
- `client_with(guard, ua)` is `client_proxied(guard, ua, None)`. `proxy(url) -> Result<reqwest::Proxy>` wraps `Proxy::all` and gives back `not a proxy URL: ...`. `client_via(guard: bool, ua, Option<&str>) -> Result<Client>` is the entry point for `--proxy <url>`. Through a proxy the address check moves to the proxy: the guard still refuses private and local literal IPs, both in the URL and on redirects, but the proxy resolves names.
- Not done (outside the card's paths): the `--proxy <url>` flag itself. main.rs needs `#[arg(long)] proxy: Option<String>` and a call to `client_via(guard, ua, cli.proxy.as_deref())?` where it calls `client(guard, ua)`. mcp.rs's fetch_page needs the same change through a Settings field. The README describes the flag and says it still has to be wired.
- Test: `guarded_client_ignores_proxy_env` (src/lib_test.rs). It binds a listener that logs request lines and answers "via proxy". Then it re-runs the test binary on the `#[ignore]`d `proxy_env_child`, with HTTP(S)_PROXY/ALL_PROXY (both cases) pointed at the listener and NO_PROXY removed, so the variables never reach the other tests. In the child, a guarded fetch of `http://` and `https://inside.test` (injected as resolving to 10.0.0.7) is refused as a private address, and a literal 10.0.0.7 is refused. The controls: an unguarded fetch of control.test does arrive through the environment's proxy, and `client_via` with an explicit proxy reaches explicit.test. The parent checks that the listener saw exactly those two requests and no inside.test or 10.0.0.7. With `.no_proxy()` taken out, the test fails.
- README: a paragraph under "Private addresses are refused".

## Hidden and invisible content (card-6, 2026-11-27)

Built on main at 082a47c (cards 1 and 2), so it does not have the card-3, card-4 or card-5 code. It touches only `content()` and what is below it, so it should merge without clashes in the fetch code.

- `content(html, url, format, full)` keeps its signature and wraps `content_inner`. The order is: `strip_invisible` on the raw HTML (this takes ANSI sequences out whole before htmd can escape their `[`), then parse, then `drop_hidden(&mut doc)`. If anything was dropped, the document is re-serialised with `doc.html()` for dom_smoothie. Readability and the whole-page path both work from that cleaned page. After conversion, `strip_invisible` runs on the body, the title and the byline. Characters written as entities (`&#x200B;`) only appear after parsing and are caught there. A readability attempt that falls through to the whole page does not add to the count.
- `drop_hidden` walks the tree. It detaches each element that has the `hidden` attribute, `aria-hidden="true"` (trimmed, any case), or an inline `style` with a `display: none` or `visibility: hidden` declaration (any case, any spacing, `!important` ignored). The element's children go with it and are not counted separately. Only inline styles count, because no CSS is run.
- `is_invisible(c)` (pub) covers tag characters U+E0000-U+E007F, zero-width U+200B-U+200D, U+2060 and U+FEFF, bidi controls U+202A-U+202E and U+2066-U+2069, DEL and C1 (U+007F-U+009F), and C0 except `\n` and `\t` (`\r` goes too). `strip_invisible(s) -> (String, usize)` (pub) removes them and counts the characters removed. An ESC takes its sequence with it: CSI `ESC [ params final`, OSC `ESC ] ... BEL|ESC \` (stopped at a newline when unterminated), or the two-character `ESC X`. The C1 CSI U+009B takes its parameters too.
- `Content` gains `removed: Removed { hidden_elements, invisible_chars }`, with `any()` and `notice() -> Option<String>`: `removed N hidden element(s) and M invisible or control character(s) a reader of the page would not see - the page may be hiding instructions`. Content is built only in lib.rs, so mcp.rs and main.rs compile unchanged.
- The report: when anything was removed, `content()` itself prints `webfetch: <url>: <notice>` on stderr. That covers the CLI and the MCP server's stderr without touching main.rs.
- Not done (outside the card's paths, src/mcp.rs and src/main.rs):
  - The MCP fetch_page result still carries the constant NOTICE. The card asks for the count in the MCP notice. In mcp.rs `fetch_page`, `"notice": NOTICE` should become `c.removed.notice().map_or(NOTICE.to_string(), |n| format!("{NOTICE}; {n}"))`, perhaps with a `"removed": {hidden_elements, invisible_chars}` field (and the outputSchema to match). Until then an agent sees the count only if its client shows the server's stderr.
  - The CLI's `--raw` prints `page.body` as served, so escape codes can still reach the terminal on that path. main.rs should print `strip_invisible(truncate_chars(&page.body, RAW_LIMIT)).0`. The README says `--raw` strips nothing.
  - Search hit titles and snippets (format_hits, mcp search_tool) are not stripped. `strip_invisible` is there for them.
- Test: `strips_hidden_and_invisible_text` (src/lib_test.rs). The page is an article with a `DISPLAY : none !important` div holding an instruction, an `aria-hidden="true"` block, a `hidden` span and a `visibility:hidden` span. It carries 15 tag characters, five zero-width characters as entities (plus one in the title), a pair of bidi controls and a red ANSI escape with its reset. For Markdown and text, through both readability and `full`, none of the secret text, no `[31m`, no ESC and no invisible character reach the title, byline or body. The visible text is all still there. The count is exactly 4 hidden elements and 32 characters, and the notice names both. A clean page reports `Removed::default()` and no notice. `strip_invisible` is checked directly on C0, C1, an OSC title sequence, a C1 CSI and `\r`, with newline and tab kept.
- README: a "Nothing hidden" bullet under "What comes out".

## Web ports only (card-7, 2026-11-27)

Built on main at 082a47c (cards 1 and 2). It touches only `Guard` in the fetch code (plus a two-field change in `with_local`), so it should merge with cards 3 to 6. If card-4's redirect policy is merged, its guard check still runs before the host check, so a hop to a refused port is refused rather than handed back.

- `Guard` gains `ports: HashSet<u16>` (the operator's extra ports). `WEB_PORTS = [80, 443]` (pub const). `Guard::allow_port(p) -> Guard` adds one and `allows_port(p)` asks.
- `Guard::check_url` checks the scheme, then the literal IP (so a private or local address still gets its own message), then `url.port_or_known_default()`. A port that is not 80, 443 or allowed gets `refusing <url>: port N is not a web port (80 or 443); --allow-port N to fetch it`. The rule is the port number, whatever the scheme: `http://h:443/` passes. The redirect policy calls `check_url` on every hop, so redirects are covered without other changes. Names on a refused port are refused before any DNS lookup.
- The operator's ports reach every guard through a process-wide `OnceLock<Vec<u16>>`. `allow_ports(ports)` (pub) sets it once, and `Guard::from_interfaces()` adds those ports. This means `client(guard, ua)`, `fetch(.., guard)` and mcp.rs's fetch_page (which builds its guard through them) honour `--allow-port` with no change to mcp.rs or to Settings. Tests build their guards with `with_local(..).allow_port(..)` and never set the global.
- main.rs: `--allow-port <PORT>` (`Vec<u16>`, repeatable), passed to `webfetch::allow_ports` first thing in main. It applies to the CLI and to `--mcp`. With `--allow-private` there is no guard, so no port is refused.
- Existing tests changed: `the_guarded_client_refuses_a_name_that_resolves_inside` fetches `http://localhost/` instead of `localhost:9`, so the resolver still gives the refusal. `refuses_this_machines_own_address` builds its guard with `.allow_port(11434)`, so the address is what refuses, not the port. The CLI and MCP tests that expect "private address" for `127.0.0.1:<port>` pass unchanged because the literal-IP check comes first.
- Test: `refuses_ports_other_than_80_and_443` (src/lib_test.rs). `:8765` and `:11434` are refused on a public host by name (`public.test`, injected), by literal IPv4 and by IPv6, through both `check_url` and a guarded `fetch_with`. `:80` and `:443`, written or by default, pass. With `.allow_port(8080)`, `:8080` passes and `:8765` is still refused, and `127.0.0.1:8080` is still refused as private. A local server 302s a guarded client to `public.test:8765` and then to `93.184.216.34:11434`, and both are refused by port on the redirect. The test makes no outbound connection.
- README: a paragraph under "Private addresses are refused", `--allow-port` in the MCP flag list, and "or port" in the exit-status line.
